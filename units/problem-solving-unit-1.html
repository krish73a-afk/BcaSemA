🛠️ PROBLEM SOLVING TECHNIQUES · UNIT I

Problem-solving & algorithms

Before coding, make sure the problem is clear. This unit teaches you to identify inputs, outputs, rules and edge cases, then turn the plan into a finite algorithm that can be traced and checked.

PICTURE IT

Before you build a toy, first ask what it should do and what pieces you have.

A program is a recipe for a very literal helper. The helper needs exact ingredients, exact steps and a clear sign that the job is finished.

  • Separate a general problem from one example input.
  • Specify input, output, constraints and special cases.

01

Problem, instance and specification

A problem is the general task; an instance supplies particular input values. A specification states allowed inputs, required outputs, constraints and special cases. Before coding, restate the task in plain language and identify what counts as a correct result. A clear specification prevents the algorithm from solving a nearby but different problem.

Simple example

Problem: find the largest value. Instance: values 7, 3 and 9. Output: 9.

Exam takeawayList input, output, constraints and edge cases before the algorithm.
02

Preconditions and postconditions

A precondition describes what must be true before an algorithm begins, such as “the array is sorted.” A postcondition describes what must be true after it finishes, such as “the target index is returned if found.” These statements make assumptions visible and give a way to reason about correctness.

Simple example

Binary search precondition: the array is sorted. Postcondition: return a matching index or report not found.

Exam takeawayState assumptions up front and describe what is guaranteed at the end.
03

Algorithm characteristics

An algorithm is a finite, ordered, unambiguous set of steps that transforms specified input into required output. It should terminate, be precise enough to execute, produce correct results for valid input and use feasible time and memory. Correctness comes first; then improve efficiency without making the steps unclear.

Simple example

To find the larger of a and b: read both, compare them, and output the greater value; define what happens on a tie.

Exam takeawayExplain finiteness, definiteness, input/output and correctness.
04

Decomposition and stepwise refinement

A large task becomes easier when split into smaller subproblems with clear inputs and outputs. Solve a main task by combining those pieces, then refine vague steps until each is precise enough to execute. This also makes code easier to build and debug because each function or section has a focused job.

Simple example

A student-score report can be split into reading scores, validating them, calculating totals and printing results.

Exam takeawayName the subproblems and show how their results combine.
05

Pseudocode and flowcharts

Pseudocode describes an algorithm in structured, language-neutral steps. A flowchart uses standard shapes and arrows to show sequence, decisions and loops. Both help plan before writing C. They should make branches and repetition explicit, including what happens when a condition is false and when the algorithm stops.

Simple example

A decision diamond “a>b?” leads to output a on yes and output b on no.

Exam takeawayUse consistent symbols or indentation and label both decision branches.
06

Tracing, testing and efficiency

A trace follows an algorithm's variables step by step for a chosen input. Testing checks normal cases, boundaries and unusual inputs against expected results. Efficiency considers resources such as time and memory; it matters after correctness is established. Small examples can expose a flawed condition, but a single successful case does not prove correctness for every valid input.

Simple example

For a maximum-finder, test one value, equal values, a maximum at the start and a maximum at the end.

Exam takeawayShow test inputs, expected outputs and why they cover different cases.
07

Input, output and boundary cases

Before planning a solution, write exactly what input is valid, what result is required and any size or range limits. Boundary cases sit at the edges of those rules, such as an empty list, zero, a negative value or the largest allowed size. Handling them deliberately prevents a correct-looking algorithm from failing on an important case.

Simple example

For an average, zero inputs must be handled before dividing by the count.

Exam takeawayList normal, smallest, largest and unusual inputs before describing the algorithm.
08

Correctness, termination and feasibility

A useful algorithm must do more than give the right result once. Correctness means it works for every valid input; termination means it eventually stops; feasibility means its time and memory are practical for the input size. A loop should show progress toward stopping, and the final answer should follow from the stated method.

Simple example

A loop that increments i toward n terminates if i increases each pass and n is finite.

Exam takeawayState why the method is correct and what condition guarantees it ends.
09

Flowchart symbols and control flow

A flowchart uses an oval for start/end, a parallelogram for input/output, a rectangle for processing and a diamond for a decision. Arrows show the direction of control. Every decision should label both outcomes; every loop should have a clear path back to the condition and a route that eventually leaves the loop.

Simple example

A “number > 0?” diamond branches to “positive” on yes and “zero or negative” on no.

Exam takeawayUse standard symbols and label the yes/no paths so the algorithm can be traced.
10

Test cases, traces and complexity

A dry run records variable values after each step. A test set should include ordinary cases, boundaries and cases that exercise different branches. After correctness, estimate how work grows with input size: one pass over n items is linear, while checking every pair is quadratic. These estimates help compare solutions as data grows.

Simple example

For n=100, a nested loop over all pairs may do roughly 10,000 checks, unlike a single pass of about 100.

Exam takeawayShow input, expected result, branch or trace, and the reason the test matters.
11

Algorithm invariants and loop reasoning

A loop invariant is a statement that is true before and after each loop iteration. To use it, show it is true at the start, remains true after one pass and helps prove the final result when the loop ends. This is a structured way to explain correctness for tasks such as summing values or maintaining a sorted prefix.

Simple example

In a running sum, after i items, total equals the sum of the first i input values.

Exam takeawayState the invariant and connect it to initialization, update and termination.
12

Pseudocode conventions and traceability

Pseudocode is language-neutral but should still use consistent indentation, meaningful names and explicit control flow. Each line should be simple enough to trace. Avoid mixing C syntax with vague English unless the question allows it. A reader should be able to identify input, decisions, repetition and output without guessing.

Simple example

FOR i ← 1 TO n; total ← total + score[i]; END FOR

Exam takeawayUse indentation and explicit loop boundaries so the method is unambiguous.
13

Flowchart decisions and loop exits

Every decision diamond should have clearly labelled branches, commonly Yes and No. A loop should return to the condition only after the body updates the values that affect it. Show a clear exit path and make sure the stop condition is reachable. This visual review can catch a missing update or a branch that never ends.

Simple example

A digit loop returns to n>0 after n becomes n/10; the No branch exits to the result.

Exam takeawayTrace both branches and prove the loop can reach its exit.
14

Time complexity and growth

Time complexity describes how an algorithm's work grows as input size n grows, ignoring machine-specific details. A single pass is O(n); nested loops over n items may be O(n²); repeatedly halving a range is O(log n). Complexity helps compare scalability but does not by itself prove an algorithm is correct or fastest for tiny inputs.

Simple example

Binary search uses about log₂n comparisons, while linear search may inspect all n items.

Exam takeawayCount the dominant operations and state what n represents.
15

Problem statements, inputs and outputs

Before designing an algorithm, rewrite the task in your own words and list its inputs, required outputs, constraints and assumptions. Clarify units, allowed ranges and what counts as a valid result. Hidden assumptions are a common source of programs that work on the sample but fail on real inputs.

Simple example

For average marks, clarify number of subjects, whether marks are integers, what happens when there are no marks and how rounding is reported.

Exam takeawayMake an input–process–output table and state one boundary case.
16

Decomposition and abstraction

Decomposition splits a large task into smaller tasks with clear responsibilities. Abstraction hides details that are not needed at the current level. A useful decomposition keeps each part understandable and gives it a defined input and output; excessive splitting can create needless coordination.

Simple example

A library system can separate search, loan eligibility, issue transaction and due-date calculation.

Exam takeawayBreak the task into named subproblems and state what information passes between them.
17

Algorithm properties and correctness

A good algorithm is finite, unambiguous and effective, and it produces the required result for every valid input. Correctness is stronger than working on one example. Use a precondition to describe valid starting states and a postcondition to describe the promised result; then reason about how each step preserves the goal.

Simple example

For maximum of a nonempty list, initialize max to the first item and update it whenever a larger item is found.

Exam takeawayState the input condition, explain why the steps terminate and justify the output.
18

Dry runs and trace tables

A dry run executes an algorithm by hand on a chosen input. A trace table records variable values after each important step, making updates and loop conditions visible. Include a typical case and an edge case, such as the smallest input or repeated values, because a single happy path is weak evidence.

Simple example

For sum=0 and values 4,−1,3, a trace records 0→4→3→6 and confirms the final total.

Exam takeawayShow iteration number, condition and updated variables in a table.
19

Boundary cases and test design

Test cases should cover normal input, minimum and maximum values, empty or single-item data when allowed, repeated values and invalid input. Equivalence partitioning groups inputs expected to behave similarly; boundary-value testing focuses near limits where mistakes are common. Tests reveal defects but do not by themselves prove correctness.

Simple example

If age must be 18–60, test 17, 18, 19, 59, 60 and 61, not only age 30.

Exam takeawayFor each test, state the behavior it is meant to check and the expected result.
20

Algorithm efficiency and trade-offs

Efficiency considers resources such as time and memory as input grows. A simple algorithm may be best for small data because it is easier to understand, while a more efficient method can matter at scale. Compare methods using the same input assumptions and explain the trade-off rather than calling one universally best.

Simple example

Checking every pair in n items uses roughly n² comparisons; sorting first may make later lookup cheaper but adds sorting work.

Exam takeawayDescribe how work changes with input size and mention memory or clarity trade-offs.

How the unit fits together

Connect the definitions, methods and applications before you start memorizing.

The quality of a solution depends on whether the program solves the stated problem for all valid inputs, not just the sample. A specification makes the input, output and constraints explicit. Preconditions expose assumptions; postconditions describe guarantees. Decomposition turns a large task into smaller transformations that can be reasoned about independently. Pseudocode is useful because it describes logic without syntax distracting from the idea. Tracing reveals what variables do on a particular case; testing adds many cases but does not by itself prove a program correct. Efficiency comes after correctness: measure likely time and memory needs and improve only while preserving a clear argument for why the method works.

Quick recap: teach these links back

01

Define the task before choosing a solution

A problem is the general task; an instance is one set of actual values. State what input is allowed, what output is required, and any constraints. A precondition says what must be true before the algorithm runs; a postcondition says what should be true after it finishes.

02

A dependable algorithm has clear properties

An algorithm is a finite, ordered set of unambiguous steps. It should accept valid input, produce the required result, terminate, and use practical time and memory. Correctness comes first: a fast answer that is wrong is not a solution. Then consider efficiency and clarity.

03

Break, trace and improve the plan

Divide a task into smaller parts, write pseudocode or a flowchart, and trace the steps with an example. Include boundary cases such as zero, one, equal values and largest allowed input. Test normal and unusual cases, then review whether the result matches the specification.

Follow every step

Try each task yourself first, then compare your working with the explanation.

EXAMPLE 1

Design a larger-of-three algorithm

TaskRead a, b and c and output the largest.

  1. Input: three comparable values. Output: one value that is at least as large as each input.
  2. Initialize largest=a.
  3. If b>largest, set largest=b. If c>largest, set largest=c.
  4. Output largest. Trace equal values and cases where the maximum is first, second or third.
Answer and reason

The algorithm works by maintaining the invariant that largest is the greatest value seen so far.

EXAMPLE 2

Choose tests from the specification

TaskFor the larger-of-three task, choose useful tests.

  1. Ordinary case: (4,9,2) should return 9.
  2. Maximum first and last: (10,3,7)→10; (2,4,8)→8.
  3. Tie case: (5,5,1) should return 5.
  4. If input restrictions allow negatives, include (−7,−2,−9)→−2.
Answer and reason

These tests target position, ties and range assumptions instead of repeating one ordinary case.

QUESTION 1What is an algorithm? List its main characteristics.+

An algorithm is a finite, ordered set of unambiguous steps that transforms specified input into the required output. It should terminate, be precise enough to execute, accept valid input, produce the correct result and use feasible resources. For example, to find the larger of two numbers: read a and b; if a>b output a, otherwise output b. State what happens when a=b if the problem needs a distinct tie rule.

QUESTION 2Explain the problem-solving cycle used before coding.+

First restate the problem in your own words. Identify input, output, constraints and unusual cases. Plan a method and split it into smaller tasks. Trace the method on a small example and check that it covers boundary cases. Write pseudocode or a flowchart, implement one part at a time, compile and test, then review correctness and clarity. This cycle catches mistaken assumptions before they become code defects.

WORK IT THROUGH

Plan an algorithm to find the larger of two numbers.

  1. Input: a and b. Output: the larger value; state whether equal values may return either one.
  2. Compare a and b. If a>b, output a; otherwise output b.
  3. Trace a=4,b=9; a=9,b=4; and a=b=5 to confirm the tie rule.
